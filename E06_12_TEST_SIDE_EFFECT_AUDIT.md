# E06-12 — Database test side-effect and isolation audit

## Scope and safety

Audited the RC3 `backend/tests` source for explicit transaction boundaries and SQL side effects.
This is a source audit only. It does not connect to PostgreSQL, execute migrations, or change any
database. The dedicated `industrial_ai_v18_e06_acceptance` database remains untouched.

## Findings

The scan found 84 source lines matching write/DDL/transaction patterns. These are occurrences,
not 84 independent defects.

### A. Deliberate per-test durable writes with autocommit

| Test module | Observed behavior | Isolation assessment | Required action |
|---|---|---|---|
| `test_agent_atomic_v03.py` | autocommit enabled; writes workflow/agent state | Must confirm every row is keyed by fresh workflow/request IDs | Keep autocommit only if helper semantics require it; verify fresh IDs and repeated run |
| `test_agent_governance_v02.py` | autocommit enabled | Workflow-scoped records; inspect uniqueness and assertions | Verify test-specific workflow IDs and no fixed-key collisions |
| `test_agent_harness_postgres.py` | autocommit enabled; seed + workflow + durable MRP + agent draft | `seed()` uses shared baseline; workflow ID generated by application | Do not blanket-disable autocommit; verify idempotent seed and unique workflow key |
| `test_workbench_postgres.py` | autocommit enabled | Multiple workbench integration flows | Inspect each test's created identifiers and persistent side effects before any rewrite |
| `test_workflow_postgres.py` | autocommit enabled | Workflow/outbox persistence is the behavior under test | Unique workflow/event IDs required; durable rows expected |
| `test_workflow_v03_postgres.py` | autocommit enabled; explicit outbox UPDATEs | Tests retry/lease state transitions | Unique message IDs required; durable transition is intentional |
| `test_workflow_worker_postgres.py` | autocommit enabled; workflow/outbox writes | Worker claim/retry/dead-letter behavior requires committed visibility | Unique workflow/event IDs required; durable rows expected |

**Decision:** do not globally switch these fixtures to `autocommit=False`. Doing so can change
the behavior under test and invalidate worker/concurrency semantics. Instead, enforce unique
test namespaces and explicit assertions that rows belong to the current test's IDs.

### B. Explicit commits and concurrency

| Test module | Observed behavior | Isolation assessment | Required action |
|---|---|---|---|
| `test_mcp_v15_security_hardening_pg16.py` | commits seed state to coordinate two independent CAS sessions; retains append-only audit rows | Intentional persistence required for the two-session race; UUID call/event IDs avoid collisions | Keep isolated to the V15 test DB or a dedicated V15 schema/database; record persistent evidence as expected, not cleanup failure |
| `test_mcp_v15_full_batch_pg16.py` | explicit commit after DB setup | Needs review of setup scope and whether it is immutable fixture data | Confirm target database identity and ensure unique keys |
| `test_v15_portfolio_authorized_e2e_pg16.py` | commits runtime and business DB setup; explicit cleanup deletes tenant-scoped rows | Cleanup exists but must be checked for exception safety and both DBs | Ensure cleanup in `finally`; preserve separate runtime/business DSNs |
| `test_v18_phase4_live_pg16.py` | creates a random schema and drops it in `finally` | Good isolation pattern; cleanup is scoped to generated schema | Retain; ensure schema identifier remains generated internally |

### C. Transaction rollback already used

- `test_erp_v11_stage3_postgres.py`: explicit rollback probes.
- `test_srm_v14_pg16.py`: corruption probe wrapped in a transaction that is deliberately aborted.
- `test_mcp_v15_final_gate_pg16.py`: rollback/savepoint around privilege probes.
- `test_mcp_v15_pg16.py`: fixture rollback and savepoint around append-only rejection.
- `test_pg_contract_v02.py`: uses controlled lock/transaction behavior; do not rewrite without preserving lock semantics.

These are not candidates for blanket cleanup changes.

### D. Shared baseline seed risk

The V12/V13/MES/MRP tests call shared `seed()` and `seed_effective_bom()` helpers.
These are intended to be idempotent, but they write fixed baseline identifiers. They can interfere
with concurrent suites if those suites mutate the same baseline rows.

**Required gate:** run the E06 integration suite serially against its dedicated database; do not
run these fixed-seed suites concurrently until the seed contract is proven idempotent and
non-mutating for existing rows. Prefer per-test schema/database isolation for future parallel runs.

## Release blockers carried forward

1. E06-12 is a source audit, not yet a full proof of cross-test repeatability.
2. Need targeted review of every `autocommit=True` fixture and seed helper implementation.
3. Need verify `finally` cleanup paths for committed two-DB E2E tests.
4. Need keep historical V12/V13/V14/V15 tests on their explicitly designated DBs; do not redirect
   those suites to the new E06 DB merely by changing environment variables.
5. Need run twice, serially, the E06 integration gate and compare test-created row deltas.
6. Need live PG16 + Python 3.14 + Windows PowerShell 5.1 + browser E2E before final sign-off.

## E06-12 conclusion

No broad autocommit/commit rewrite is justified by the source evidence. Durable commits, worker
leases, append-only audit, and two-session CAS are part of the tested contracts. The safe next
engineering action is targeted test-ID/cleanup verification and serial repeatability testing,
not blanket transaction rollback.
